# Dual-Paraboloid Map ベイカー + 反射検証ビューア 実装仕様

## 0. このドキュメントについて

対象実装者: Claude Code
実装ターゲット: three.js / WebGL2（TypeScript + 素の GLSL）
スコープ: equirect HDRI から Dual-Paraboloid Map（以下 DP マップ）を焼くベイカー + 反射描画の検証ビューア

**この仕様の性質**: これは「DP マッピングが本当に有効かを自分で検証するための計測装置」を作る仕様です。見た目のデモではありません。したがって §7 の受け入れ条件（特に 7-1 と 7-4）を満たさない実装は、絵が出ていても不合格として扱ってください。

数式については §3 に正規形を書いていますが、**実装者はこれを信用せず §7-1 の往復テストで検証すること**。符号規約は出典によって異なり、ここに書いた式も転記ミスの可能性があります。テストが通らなければ式ではなくテストを疑う前に式を疑ってください。

## 1. 背景と目的

GTA V は環境キューブマップ（128×128×6面、毎フレーム生成）を DP マップ（128×128×2半球）に変換して反射に使っています。動機は 2 つ:

1. フラグメントシェーダのテクスチャアクセス先を 6 面から 2 半球に削減
2. キューブマップの面境界のシーム問題を回避（面ごとに独立してミップマップすると境界に継ぎ目が出る、旧世代 GPU は面をまたぐフィルタリング非対応）

DP 投影は**上下方向の反射ディテールを保ち、横方向を犠牲にする**特性を持ちます。GTA V でこれが成立したのは、車のルーフやボンネットが上を向いており、上からの反射が良ければ十分だったからです。

**重要な前提**: 上記の動機 2 は、seamless cube map filtering（D3D10.1 以降 / OpenGL ES 3.0 / WebGL2）が普及した現在すでに解消済みです。したがって本プロジェクトのゴールは「DP を採用すべきか」を判断するための定量データを得ることであり、DP が優れているという結論を前提にしてはいけません。ビューアは常にリファレンス実装との数値比較を出せる構成にしてください（§5-3）。

## 2. 入力データ

### 2-1. テスト用 HDRI

`historic_cloister_passage_1k.exr`（Poly Haven, CC0）

実測済みの性質:

| 項目 | 値 |
|---|---|
| 解像度 | 1024 × 512（2:1 = equirectangular / latlong） |
| チャンネル | R, G, B（アルファなし） |
| ピクセル型 | 各チャンネル 32-bit FLOAT |
| 圧縮 | PIZ |
| 値域 | min 0.0044 / max 268 |
| 負値・NaN・Inf | すべて 0 個 |

→ 負値クランプ処理は**このファイルには不要**ですが、他の HDRI を読ませる可能性があるためベイカーには入れておくこと（EXR は仕様上負値・Inf・NaN を持てる）。max 268 は half の上限 65504、`R11G11B10F` の上限のいずれにも収まるため、中間バッファの型で困ることはありません。

### 2-2. このHDRIの輝度分布（DP との相性）

天頂を 0° として緯度帯ごとの平均輝度:

| 天頂からの角度 | 平均輝度 |
|---|---|
| 0–45° | 約 0.22 |
| **45–67°** | **2.38** |
| 67–90° | 0.72 |
| 90–180° | 0.35 – 0.58 |

**明るさが水平寄り（天頂から 45–67°）に約 10 倍集中しています。** これは DP が最も潰す領域です。つまりこの HDRI は DP にとってほぼ最悪ケースであり、それを承知の上で「DP の弱点を可視化するサンプル」として使います。

実装者への含意: このデータで「DP のほうが綺麗」という結果が出たら、実装が間違っています。水平方向の劣化が観測されるのが正常です。

### 2-3. 合成テストパターン（必須）

実 HDRI とは別に、以下をプロシージャルに生成して equirect として入力できるようにしてください。§7-4 の検証に使います。

- **緯度経度グリッド**: 10° 刻みの線。天頂/天底と水平で線の太さが同じになるよう、角度基準で描くこと（UV 基準で描くと極で潰れて検証にならない）
- **方向カラーマップ**: `dir * 0.5 + 0.5` を RGB に出力。方向の取り違えを一目で検出できる
- **単一の明るいディスク**: 指定した方向に立体角固定の光源。DP の解像度異方性を定量する

## 3. 数式（正規形）

DP 空間は軸を Z とします。2 枚のマップを `MAP_A`（−Z 側）/ `MAP_B`（+Z 側）と呼びます。「front / back」という呼称は出典によって指すものが逆になるため使いません。

`d` は正規化された方向ベクトル、`q = s*s + t*t`。

### 3-1. Forward（方向 → 平面座標）

```
MAP_A:  s =  d.x / (1.0 - d.z)      t =  d.y / (1.0 - d.z)
MAP_B:  s = -d.x / (1.0 + d.z)      t = -d.y / (1.0 + d.z)
```

### 3-2. Inverse（平面座標 → 方向）

```
MAP_A:  d = vec3( 2.0*s,  2.0*t,  q - 1.0 ) / (q + 1.0)
MAP_B:  d = vec3(-2.0*s, -2.0*t,  1.0 - q ) / (q + 1.0)
```

### 3-3. Inverse は全平面で正規化されている（重要）

`|d|² = (4s² + 4t² + (q-1)²) / (q+1)² = (q² + 2q + 1) / (q+1)² = 1`

**これは q の値に関係なく成立します。** つまり `q > 1`（単位円の外）でも式は有効な方向を返し、反対側の半球に滑らかに連続します。

| q | MAP_A の d.z |
|---|---|
| 0 | −1（中心 = 軸の負方向） |
| 1 | 0（水平） |
| 2 | +1/3 |

この性質が本実装の設計上の要になります。単位円の外に未定義領域が存在しないため、**正方形テクスチャ全体を有効なデータで埋められ、ミップマップ時に境界からゴミが滲まない**。さらに 2 枚のマップが水平付近で重複するため、シームをブレンドで消せます。

Kyle Hayward（graphicsrunner）がコメント欄で「2 枚のマップが接する継ぎ目の処理が一番の問題」と述べているのは、この重複領域を用意していない実装の話です。本実装では意図的に用意します。

### 3-4. ガードバンド（R パラメータ）

テクスチャ UV と `(s,t)` の対応に倍率 `R` を入れます。

```
(s, t) = (uv * 2.0 - 1.0) * R
uv     = (vec2(s, t) / R + 1.0) * 0.5
```

`|d.z| = w` の方向を MAP_A で引くとき、サンプル半径は最悪ケース（軸に平行な方向）で
`|(s,t)| = sqrt((1+w)/(1-w))` になります。これが `R` 以下でなければテクスチャ外を引きます。したがって:

```
w_max = (R² − 1) / (R² + 1)
```

| R | ブレンド可能な半幅 w_max |
|---|---|
| 1.00 | 0.000（ハードスイッチのみ） |
| 1.10 | 0.095 |
| **1.15** | **0.139** |
| 1.25 | 0.220 |

既定値: `R = 1.15`, ブレンド半幅 `w = 0.12`（w_max に対して余裕を取る）

`R = 1.0` + ハードスイッチも選択できるようにし、両者を UI で切り替えて比較できること。これがシーム問題の有無を示す一次証拠になります。

### 3-5. マップ選択とブレンド

```glsl
// d は DP 空間の正規化方向
float a = smoothstep(-w, w, d.z);   // 0 → MAP_A のみ, 1 → MAP_B のみ
// a が 0 / 1 のときは片方だけをフェッチして分岐を省くこと
vec3 c = mix(sampleMapA(d), sampleMapB(d), a);
```

ブレンド時は両マップから引いた値が本来同一の放射輝度を指すため、平均しても輝度が変わりません。ここで暗くなる・二重像になる場合は forward/inverse の符号か basis 行列が誤っています。

### 3-6. World ↔ DP 空間

DP の解像度は軸方向に集中します。GTA V の意図（上向き面の反射を優先）を再現するため、**既定では DP 軸をワールド上方向（three.js の +Y）に合わせます。**

- `dpBasis: Matrix3` として設定可能にする
- 既定値は「ワールド +Y を DP +Z に写す回転」。開始点として: 行 `[1,0,0]`, `[0,0,-1]`, `[0,1,0]`
- **行列式は +1 でなければならない。** `(x,y,z) → (x,z,y)` のような単純な軸入れ替えは行列式 −1 の鏡映で、反射像が左右反転します。これは絵を見ても気づきにくいので §7-1 で機械的に検査すること

### 3-7. Equirect のサンプリング

**three.js の `equirectUv`（`ShaderChunk/common.glsl.js`）と完全に同じ式を使うこと。** 参考として現行の形は以下ですが、実装時に three.js のソースを開いて突き合わせてください。

```glsl
float u = atan(dir.z, dir.x) * RECIPROCAL_PI2 + 0.5;
float v = asin(clamp(dir.y, -1.0, 1.0)) * RECIPROCAL_PI + 0.5;
```

理由: リファレンス経路（§5-3）は three.js 内蔵の equirect / PMREM を使います。DP 経路が別の式で equirect を引くと、比較している差分に「マッピング式の違い」が混入して測定が無意味になります。

テクスチャのラップは u が `RepeatWrapping`、v が `ClampToEdgeWrapping`。

## 4. ベイカー仕様

### 4-1. 方式

GPU の全画面パスで焼きます。Node.js の CLI ではなくブラウザ内で実行してください。理由:

- Node 側に EXR デコード / エンコードのツールチェーンを持ち込む必要がない（three.js の `EXRLoader` をそのまま使える）
- ベイクとランタイムでサンプリングコードを共有でき、経路差による誤差が混入しない
- ビューアと同一アプリになるため、パラメータを変えて即座に焼き直せる（これが検証作業の主要ループ）

### 4-2. 処理

出力先: `WebGLRenderTarget` 2 枚（MAP_A / MAP_B）、`THREE.HalfFloatType`、`RGBAFormat`

各出力テクセルについて:

1. テクセル内に `N × N` の層化サンプル点を取る（ジッタあり）
2. 各点の `(s,t)` を §3-4 で求め、§3-2 で方向に変換
3. `dpBasis` の逆行列で DP → world に戻す
4. §3-7 で equirect をフェッチ
5. 平均して出力

`(s,t)` 領域で一様サンプルした平均が、そのまま DP テクセルが保持すべき値になります。equirect 側の極オーバーサンプリングはこの手順で自動的に吸収されるので、別途の立体角重み付けは不要です。

### 4-3. サンプル数とミップ

DP テクセルがカバーする立体角は中心付近で小さく、水平付近（`q → 1`）で大きくなります。したがって必要サンプル数は場所によって 1 桁以上変わります。

- **Phase 1（まずこれ）**: equirect をミップ付きで読み込み、テクセルごとの立体角比から明示 LOD を計算して `textureLod` で引く。`N = 8`
- **フォールバック**: mip 0 固定で `N = 32`。遅いが単純。Phase 1 の結果検証用に残しておくこと

`N = 1` でも動くようにしておき、UI で切り替えてエイリアスが出ることを確認できるようにしてください（サンプリングが効いている証拠になります）。

### 4-4. パラメータ

| 名前 | 型 | 既定 | 備考 |
|---|---|---|---|
| `resolution` | number | 128 | 64 / 128 / 256 / 512 / 1024 |
| `R` | number | 1.15 | ガードバンド倍率 |
| `supersamples` | number | 8 | 片辺の数（N×N） |
| `useAnalyticLod` | boolean | true | false でフォールバック経路 |
| `generateMipmaps` | boolean | true | |
| `dpBasis` | Matrix3 | §3-6 | |

`resolution = 128` は GTA V の実測値です。既定値として残し、上げたときに何が改善するかを見るための基準線として扱ってください。

### 4-5. ミップマップ

**MAP_A / MAP_B は必ず別テクスチャにすること。** 1 枚のアトラス（横並び 2 タイル）にまとめてはいけません。ミップ生成時にタイル間で滲み、DP の売りである「シームなしにミップできる」性質を自分で壊すことになります。

WebGL2 の `DataArrayTexture`（2 レイヤー）は許容します。レイヤー間は滲みません。

### 4-6. 書き出し（任意 / Phase 2）

ビューアはレンダーターゲットを直接サンプルするため、ファイル出力は必須ではありません。必要になった場合の形式:

- **既定**: 生の `Float16Array` を `.bin` + JSON サイドカー（解像度・R・basis・チャンネル順を記録）。実装が数行で済み、検証用途では交換形式に意味がない
- PNG エンコードのプレビュー（トーンマップ済み）はデバッグ用に別途あると便利
- EXR / KTX2 は必要が生じてからでよい。EXR ライタの実装に時間を使わないこと

## 5. ビューア仕様

### 5-1. 構成

- `WebGLRenderer`（WebGL2）+ `ShaderMaterial`（素の GLSL）
- three.js は `three@0.185.x` 系を pin。npm の最新表示は 0.185.1 でしたが、実装時に確認して固定してください
- 注意: r183 以降、機能追加の重心が `WebGPURenderer` / TSL（Three Shading Language）側に移っているという情報があります。本仕様は「シェーダ数式を直接読み書きしたい」用途のため素の GLSL で書きますが、長期運用するなら TSL 化の検討が必要になる可能性があります。今回の判断としては GLSL のままで進めてください

### 5-2. シーン

- 背景: equirect を `EquirectangularReflectionMapping` で表示（リファレンス）
- 反射体（切り替え可能）:
  - **球** — 必須。シームと解像度異方性が最も出る形状。Hayward が「球ではシームが見える」と指摘しているのがここ
  - **平たい上向き面**（ボンネット相当） — GTA V の想定ケース。DP が有利に働くはずの形状
  - トーラスノット or 十分に複雑な形状 — シームが隠れるケースの確認
- ライティングは不要。ミラー反射のみ（`reflect(viewDir, normal)` を DP で引くだけ）

### 5-3. 3 経路の同時比較（本体機能）

同一シーン・同一カメラで以下を切り替え / 並置できること:

1. **DP 経路** — 本実装
2. **Cubemap リファレンス** — equirect から生成したキューブマップを `textureCube` で引く。同解像度・同ミップ設定で揃える
3. **Equirect 直サンプル** — グラウンドトゥルース（中間表現を経由しない）

表示モード:

- 単独表示
- 左右分割（ドラッグで境界移動）
- **差分表示** — 経路 A と B の差を可視化。倍率スライダ付き。`abs(a-b) * gain`
- **数値** — 画面内の相対 RMSE と最大誤差を毎フレーム表示。これがないと「検証」になりません

### 5-4. コントロール（lil-gui 等）

ベイク側: §4-4 の全パラメータ（変更したら自動で焼き直し）
描画側: `w`（ブレンド半幅）、ハードスイッチ / ブレンド、ミップ ON/OFF、反射体の形状、比較モード、差分ゲイン
デバッグ: MAP_A / MAP_B を画面隅にクアッドで生表示（単位円と R の枠線をオーバーレイ）

ラベルは操作結果をそのまま書いてください（「ブレンド」ではなく「シームをブレンドする」）。値は数値も併記すること。

## 7. 受け入れ条件

### 7-1. 往復テスト（TS、自動テスト）

- ランダムな正規化方向 10,000 本について forward → inverse の誤差 < 1e-5。MAP_A / MAP_B 両方
- 上記を `d.z < 0` は MAP_A、`d.z > 0` は MAP_B で実施。加えて `|d.z| < 0.12` の帯では**両方のマップで**成立すること（ガードバンドが機能している証拠）
- inverse の出力が `q ∈ [0, 2R²]` の全域で単位長（誤差 < 1e-6）
- `dpBasis` の行列式が +1（誤差 < 1e-6）。鏡映になっていないこと
- `w_max = (R²−1)/(R²+1)` を満たす `R` と `w` の組でのみブレンドが有効化される

### 7-2. GPU 側の一致

`dpMath.glsl` の forward / inverse を小さなレンダーターゲットに出力し、TS 実装との差が 1e-4 未満（half 精度を考慮）。

### 7-3. リファレンスとの数値一致

- §5-3 の 3 経路が同一シーンで動き、RMSE が表示される
- `resolution` を 64 → 1024 に上げたとき、DP 経路の RMSE が**単調に減少する**こと。減少しなければサンプリングかミップの実装に問題があります
- 特定の数値目標は設けません。目的は絶対値ではなく、条件を変えたときの相対変化を観測することです

### 7-4. DP 特性が正しく出ていることの確認（必須）

**§2-3 の緯度経度グリッドを equirect として入力し、DP 経路で描画したとき:**

- 天頂 / 天底方向のグリッドが細かく、水平方向のグリッドが粗く潰れて見えること
- 単位円の境界（`q = 1`）が水平方向に一致すること
- `R = 1.0` + ハードスイッチにすると水平線上に不連続が現れ、`R = 1.15` + `w = 0.12` にすると消えること

**この非対称性が出ない実装は、DP になっていません。** 等方的に見えるなら、どこかで equirect をそのまま使っているか、basis が効いていない可能性があります。

### 7-5. 実 HDRI での確認

`historic_cloister_passage_1k.exr` で、§2-2 の輝度分布どおり**水平方向の反射が最も劣化する**ことを差分表示で確認できること。天頂側の劣化が大きく見える場合は軸の向きが逆（`dpBasis` の符号）です。

## 9. Phase 2（余力があれば）

**Octahedral mapping との比較。** DP と同じ枠組み（同解像度・同ミップ設定・同 RMSE 計測）で octahedral 経路を追加し、4 経路比較にする。

理由: 1 枚のテクスチャで済み、シームの扱いが単純で、DP より面積歪みが小さいという主張があります。ただしこれは仕様作成者の見立てであり一次資料を確認していません。実装前に octahedral 側の出典を自分で当たってください。

これを入れると、本プロジェクトは「DP の実装」から「環境マップのパラメタライゼーション比較装置」になり、はるかに有用になります。
